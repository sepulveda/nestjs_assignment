1. Explique la diferencia entre Middleware, Guard, Interceptor y Pipe en NestJS.
   -Si bien todas estas herramientas son ejecutadas antes de que la petición llegue al route handler en orden middleware->guard->interceptor o pipe->route, cada una se especializa en diferentes casos. Los middleware son utilizados a nivel global en todas las rutas para autenticar. Guards son utilizados para realizar control de acceso en base a alguna condición (roles de usuario, usuario activo, etc.). Interceptors son utilizados tanto en request como en response para modificar los datos antes de ser enviados al route handler o al cliente. Finalmente, Pipes son utilizados principalmente para validar la integridad de datos y que el route handler reciba los datos en el formato que requiere.
2. ¿Cómo implementaría autorización basada en roles?
   -Implementaría una propiedad Rol en la tabla que almacena los datos de los usuarios del sistema, enviaría la id del usuario en la petición desde el cliente e implementaría un Guard de tipo RolesGuard donde validaría si el usuario tiene el rol requerido para continuar con la petición en específico.
3. ¿Qué problemas aparecen cuando un backend crece mucho y cómo NestJS ayuda a resolverlos?
   -El problema principal es la escalabilidad y el rendimiento del backend debido a la gran cantidad de peticiones que conllevan multiples endpoints junto con los tiempos de espera que conllevan las peticiones a endpoints que reciben más peticiones que otros. NestJS permite la mitigación de estos problemas mediante el uso de clusters, ejecutando multiples instancias de microservicios en el mismo puerto.
4. ¿Cómo manejaría configuración por ambiente (development, staging, production)?
   -Configurando la variable de entorno NODE_ENV a dev/staging/prod al momento de ejecutar el backend (agregar node_env=development al script start:dev en package.json por ejemplo) y manejando distintos archivos .env para cada stage.
5. ¿Cómo evitaría que dos usuarios compren el último producto disponible al mismo tiempo?
   -Marcaría el elemento como no disponible desde que el primer usuario inicie el flujo de compra y pago, con un tiempo límite para realizar dicho pago. En el caso de que otro usuario trate de iniciar el flujo de compra y pago se validará si el producto sigue disponible antes de iniciar el proceso de compra y se le informará al usuario si no está disponible. Si el usuario que inició el flujo de compra o pago cancela la compra o no la finaliza en el tiempo asignado el producto volverá a estar disponible y se liberará para poder ser comprado por otro usuario. Es posible agregar métodos que validen el stock disponible en tiempo real si es requerido.
